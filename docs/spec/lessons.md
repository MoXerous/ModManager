## 1. أخطر نمط متكرر: **عامل خيط خاص323 يتجاوز دورة الحياة المُختبَرة**

| | |
|---|---|
| **الأثر** | انهيار الواجهة عند الإغلاق بعد تشغيل بحث |
| **الدليل** | `PHASE16_11_3_SEARCH_GLOBAL_WORKER_STABILITY_FIX_REPORT.md` |

**القصة:** فُصل مسار البحث (`search_thread` / `search_worker`) عن خط `_run_worker()` العام لأجل تحسين تجربة المستخدم. أثره: تفاوت في التنظيف واستبدال الخيوط، فأصبح **التطبيق ينهار عند الإغلاق بعد بحث أو بعد بحث متكرر** — رغم أن كل اختبار آلي كان يمرّ.

**السبب الجذري المُعلن:** الانحراف عن دورة حياة العامل المستقرة. **الإصلاح:** إعادة البحث إلى `_run_worker()` مع الحفاظ على السلوك المطلوب (طلب جديد يُصطف، الجارٍ يُلغى تعاونياً، نتيجته القديمة تُهمَل، الجديد يبدأ بعد تنظيف الخيط بالكامل).

### القاعدة لنا

> **خيط واحد، خيط واحد.** أي مسار تنفيذ جديد يمرّ بنفس مدير المهام ولا يتجاوزه.
> الاختبارات الآلية **لا تكشف** أعطال الإغلاق ولا أعطالthread-affinity في Qt: اختبار يمرّ بينما البرنامج ينهار عند الخروج.
> **اختبار الإغلاق обязателен** لكل ميزة تلمس خيوطاً. (`foundations.md` §15 يوجب قياس «تجمّد الواجهة» ونعتمد نفس المنطق.)

> **ملاحظة عن `tokio`:** المشكلة analog. `tokio::spawn` منفصل عن بقية المهام، أو `spawn_blocking` يتجاوز الsemaphore، ينتج نفس класс الخلل: مهمة هاربة تنهي العملية أو تُبقي قفلاً. اجعل **كل** géénTask يمرّ بملك واحد معلوم.

## 2. نتايج قديمة بعد استبدال: **المهمة الملغاة تُفسد(Result) الجديد**

| | |
|---|---|
| **الأثر** | بحث ملغى يفرّغ النتائج الجديدة أو يستبدلها |
| **الدليل** | `PHASE16_11_7_IMMEDIATE_SEARCH_INTERRUPT_FIX_REPORT.md`، `PHASE16_11_3_…` |

**القصة:** عند الإلغاء الفوري، النتيجة/الخطأ القديم يصل بعد بدء البحث الجديد فيُطبَّق على حالة العرض.

**الإصلاح المعلن:** «تُتجاهل النتائج/الأخطاء القديمة من عمليات البحث المقاطعة» + بوّابة `active-generation` قبل أي تحديث للواجهة.

### القاعدة لنا

> كل مهمة غير متزامنة تحمل **معرّف جيل (generation)**، والواجهة **ترفض** أي حدث لا يحمل الجيل النشط. هذه ليست رفاهية — بل ما يمنع عرض بيانات تخصّ طلباً ملغى.
> في Rust: `JoinHandle` + `CancellationToken` (tokio-util)، ومعرّف جيل في DTO نفسه فيتحقق منه المُستقبِل لا المُرسِل. (`foundations.md` §4: `Channels` للتقدّم — نفس المنطق.)

**ملاحظة سلبية مهمة:** `PHASE16_19_34_RESOLVER_RUN_CACHE_DIAGNOSTICS.md` يسجّل أن الكاش **مُقيَّد عمداً** بـ«عامل واحد / تشغيل واحد / خيط واحد» — «كاش دائم يشاركه خيوط متعددة **يُرجَّح أنه** يُدخل بيانات قديمة». **هذا نمط صحيح نتّبعه:** كاش داخل عملية تشغيل واحدة، لا كاش عام دائم.

## 3. الإلغاء الذي يبدو نجاحاً فارغاً

| | |
|---|---|
| **الأثر** | إلغاء استيراد يبدو «استيراداً ناجحاً بلا نتائج»؛ و`.mrpack` بلا إشارة نهائية |
| **الدليل** | `PHASE16_19_41_IMPORT_CANCEL_HARDENING_REPORT.md` |

**القصة:** `finished(path, 0)` للإلغاء — أي **رمز نجاح**. و`CancellableWorker` كان بلا إشارة `cancelled`.

**الإصلاح:** إضافة `cancelled = Signal(str)`، وربطها بـ`thread.quit` حتى تخرج الواجهة من حالة الانشغال.

### القاعدة لنا

> **الإلغاء ليس نجاحاً ولا فشلاً — هو نتيجة ثالثة.** أصناف `IpcError` (بـ`AGENTS.md` §5.3) لا يجوز أن تحوّل الإلغاء إلى `Ok` فارغ.
> وكل عملية طويلة تحتاج **حالة نهائية واحدة**؛ أي مسار يترك العملية بلا إشارة نهائية يُعتبر علّة لا نقص.



## 4. ميتافيزقا تالفة: **استيراد بلا فحص توافق**

### 4-1. المسح لا يزيل ما لم يعد موجوداً

| | |
|---|---|
| **الأثر** | بعد حذف `.jar` يدوياً، المود يبقى ظاهراً في «Saved Mods» إلى الأبد |
| **الدليل** | `PHASE16_18_2_SCAN_PRUNE_SAVED_MODS_FIX_REPORT.md` |

**السبب الجذري:** `scan_installed_folder()` و`import_installed_scan_matches_to_profile()` **كان يستوردان أو يستبدلان** فقط، ولم **يقارنا** نتيجة المسح.Metadata الموجود أصلاً.

**الإصلاح:** خيار صريح «أزل مدخلات الحفظة غير الموجودة في هذا المسح (**بيانات فقط**)».

### 4-2. القص الأعمى: «الموجود» حُسب من غير المطابقين

| | |
|---|---|
| **الأثر** | خصوصية خاطئة تحذف مدخلات سليمة |
| **الدليل** | `PHASE16_18_3_SAVED_MODS_MISSING_FILE_PRUNE_FIX_REPORT.md` |

**السبب الجذري (ممتاز التعليل):** مسار «المسح والقص» كان يستقبل `dialog.import_matches()` فقط — وهي **المشاريع المطابقة للاستيراد**، لا **المشاريع الموجودة فعلاً على القرص**. فالنتيجة: مشروع موجود على القرص لكنه **متخطّى** لعدم التوافق، يُحسب «مفقوداً» ويُقصّ.

**الإصلاح:** `InstalledScanDialog.present_project_ids()` يعيد **كل** المعرّفات المتعرَّفة في المجلد الممسوح، والقص يقارن بذلك.

### القاعدة لنا

> **«الموجود على القرص» و«المؤهَّل للاستيراد» مجموعتان مختلفتان.** أي عملية «تنظيف» تقارن بالمجموعة الصحيحة أو تحذف بيانات سليمة.
> **والتنظيف عملية تدمير بيانات — فاجعله Dry-run إلزامياً** (`foundations.md` §13.4، و`AGENTS.md` §5.4).

### 4-3. الملف المفقود يحجب تنظيف الميتافيزقا

نفس التقرير: عند تفعيل «احذف الملف المطابق» ولم يكن الملف موجوداً، كانت الدالة **تُرجع خطأ قبل** حذف بيانات البروفايل — فتبقى الميتافيزقا **عالقة**. الإصلاح: الملف المفقود لا يحجب التنظيف، والنتيجة تقول صراحةً «الملف المحلي مفقود أصلاً».

### القاعدة لنا

> **غياب الملف هدفٌ محقَّق، لا خطأ.** عند حذف ملف، النتيجة المُبلَّغة يجب أن تميّز بين «حُذف» و«لم يعد موجوداً».

## 5. السياق غير المحدد: **البروفايل المُنشأ لا يصبح نشطاً**

| | |
|---|---|
| **الأثر** | «Link Instance» ثم «Scan installed» يعملان على بروفايل **آخر** |
| **الدليل** | `PHASE16_13_PROFILE_INSTANCE_SCAN_IMPORT_METADATA_FIX_REPORT.md` |

**السبب الجذري المُعلن:** «لم تكن المشكلة عملية ملف مدمّرة، بل خطر عدم تطابق سياق/ميتايفيزقا»:

1. البروفايل الجديد كان يُختار في القائمة ولا **يُفعَّل** كسياق نشط.
2. تحرير الربط لم يُحدّث ضوابط التشغيل النشطة.
3. الكشف التلقائي كان يملأ الميتافيزقا ولا يفعّل تلقائياً مجلد mods ومزامنة الإصدار/الـloader.
4. الاستيراد لم يكن يتحقق من مطابقة إصدار Modrinth لهدف البروفايل.

### القاعدة لنا

> **لا شيء يعمل بلا «بروفايل نشط» صريح.** كل أمر تعديل يقرأ الهدف من **معرّف** في الطلب، لا من حالة واجهة ضمنية. (§5.2: الواجهة لا تلمس الملفات إلا بأوامر صريحة.)
> **«سياق البروفايل النشط» سلوك مدمج في بايثون ولا مفهوم منفصل في Rust — اجعله بارزاً.**

## 6. القوائم الطويلة: أداء يسوء ببطء

| | |
|---|---|
| **الأثر** | «اقتراح هدف مشترك» أبطأ بعد إضافة تشخيص |
| **الدليل** | `PHASE16_19_17_COMMON_TARGET_PERFORMANCE_CACHE_REPORT.md` |

**القصة:** أُضيف تشخيص ففحص المحلّل **مشاريع غير مشتركة كثيرة** على Modrinth. الحل: كاش داخل العامل (`_downloadable_versions_cache`، `_candidate_resolution_cache`)، **مقيَّد بعامل واحد** فلا تبقى بيانات قديمة عبر التشغيلات.

**القاعدة:** عند إضافة أي **تشخيص**، حِدْ ما يفحصه. التشخيص الذي يفحص «كل شيء» يحوّل مساراً سريعاً إلى آلة بطيئة.
**وحافظ على قاعدة الكاش:** داخل **تشغيل واحد**، لا عامّ دائم. (مقابل ما ورد في §2.)
