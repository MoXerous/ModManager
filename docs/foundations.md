# وثيقة الأساسات التقنية: مدير المودات والمود باكات

*مسودة 1 · 13 أكتوبر 2026 · الاسم المؤقت للمشروع: ModManager*

الحزمة المعتمدة: **Tauri 2 مع Rust** للنواة، و**React مع TypeScript** للواجهة، و**SQLite** للبيانات، ونواة مستقلة تماماً عن الواجهة. هذه النسخة تصحّح أخطاء المسودات السابقة وتجمع أفضل ما فيها.

## 1. نظرة عامة

تطبيق سطح مكتب لويندوز ولينكس لتصفح المودات والمود باكات من **Modrinth** و**CurseForge**، وتثبيتها وتحديثها وتعطيلها وحذفها لكل نسخة (Instance) من ماينكرافت. هو **ليس Launcher**: لا يشغّل اللعبة.

**الأهداف**

- أداء عالٍ: إقلاع سريع، تحميل متوازٍ، قوائم طويلة سلسة، وذاكرة لا تزيد عن التطبيق الحالي.
- واجهة حديثة وجميلة ومتسقة على النظامين.
- قابلية تطور: إضافة مصادر ومزايا دون إعادة كتابة.
- يعمل محلياً (Local-first) دون خادم إلزامي.

**خارج النطاق في الإصدار الأول:** تشغيل اللعبة، حسابات ماينكرافت، إدارة Java، وmacOS (ممكن لاحقاً لأن Tauri يدعمه).

## 3. المبررات

### 3.1 Tauri 2 (غلاف التطبيق)

- يستخدم WebView النظام (WebView2 على ويندوز، وWebKitGTK على لينكس)، فالمثبّت أصغر بكثير من Electron.
- الجزء الخلفي Rust أصلي بلا Node.js، ونظام الـ capabilities يحصر ما يستطيع الـ WebView فعله.
- تطبيق Modrinth الرسمي مبني بالفكرة نفسها (Tauri وRust)، فالنهج مجرَّب في هذا المجال.
- **لا نبني قراراً على أرقام الحجم والذاكرة التسويقية:** ذاكرة الـ WebView تُحسب في عمليات منفصلة، فنقيس تطبيقنا بأنفسنا.
- **المخاطرة:** اختلافات رسم طفيفة على لينكس. الحل: اختبار مبكر على Ubuntu وFedora ضمن الـ CI.
- **المرفوض:** Electron لثقله، وAvalonia لأنه أقل مرونة في التصميم من الويب.

### 3.2 Rust (النواة)

العمل الثقيل كله هنا: التحميل المتوازي، الهاشات، فك الضغط، وقراءة ملفات jar.

| المكتبة | الغرض |
| --- | --- |
| `tokio` | العمل غير المتزامن والمهام الخلفية |
| `reqwest` مع `rustls` | طلبات HTTP بلا اعتماد على OpenSSL في لينكس |
| `serde` و`serde_json` و`toml` | ردود الـ API، و`fabric.mod.json`، و`mods.toml` (صيغة TOML لا XML) |
| `zip` | فك المود باكات داخل `spawn_blocking` |
| `sha1` و`sha2` | التحقق من الهاشات |
| `rusqlite` مع `rusqlite_migration` | قاعدة البيانات، وتُنفَّذ استعلاماتها في `spawn_blocking` |
| `thiserror` | أخطاء نوعية في مكتبات النواة |
| `tracing` و`tracing-appender` | سجلات منظمة تُكتب في ملف دوّار |
| `directories` | مسارات بيانات التطبيق الصحيحة على كل نظام |
| `clap` | أداة سطر الأوامر |
| `wiremock` (للاختبار) | محاكاة الـ APIs |

بصمة CurseForge (MurmurHash2 على الملف بعد إزالة المسافات البيضاء) دالة صغيرة نكتبها بأنفسنا، أو نستعير دالتها من مكتبة furse بعد فحصها.

### 3.3 الواجهة

- **React + Vite + TypeScript (strict):** أكبر منظومة مكتبات، وأقل احتكاك أثناء تعلّم Rust.
- **Tailwind CSS 4:** الإعداد داخل ملف CSS (`@import "tailwindcss"`) وبإضافة `@tailwindcss/vite`، بلا ملف `tailwind.config.js` افتراضي.
- **shadcn/ui:** مكوّنات تُنسخ إلى مشروعنا وتُعدَّل بحرية (مبنية على Radix)، وتحتاج alias باسم `@` في Vite وtsconfig.
- **TanStack Query:** يغلّف استدعاءات `invoke` ويدير التحميل والأخطاء والتخزين المؤقت.
- **TanStack Virtual:** لقوائم نتائج البحث والمودات الطويلة.
- **Zustand:** لحالة الواجهة المحلية فقط (الثيم، الشريط الجانبي، التقدم الحي).
- **Wouter:** توجيه خفيف يكفي لعدد صفحات قليل.
- **React Hook Form + Zod** للنماذج، **i18next** للترجمة مع دعم RTL، **Motion** للحركة، **Lucide** للأيقونات، **cmdk** للوحة الأوامر، **Biome** للتنسيق والفحص.
- **القرار: React.** SolidJS أسرع في التحديثات الدقيقة لكن مكتباته أقل، فاخترنا React. وبما أن النواة منفصلة، يبقى استبدال الواجهة لاحقاً ممكناً.

### 3.4 الاتصال بين الواجهة والنواة

- الواجهة لا تلمس نظام الملفات ولا الشبكة ولا SQL مباشرة: كل شيء عبر **أوامر Tauri** (`#[tauri::command]`) بأنواع صريحة.
- **Channels لتقدم التحميل لا Events:** وثائق Tauri تصفها بأنها سريعة ومرتّبة وتُستخدم داخلياً لتقدم التنزيل. ونخفف التحديثات من جهة Rust إلى نحو 100-250 مللي ثانية.
- نرسل البيانات **دفعات** (قوائم كاملة بصفحات) بدل استدعاء IPC لكل ملف.
- أنواع TypeScript تُولَّد من Rust بمكتبة (`ts-rs`).

## 4. معمارية النواة

### 4.1 المبدأ

النواة مكتبة Rust **لا تعرف شيئاً عن Tauri أو React**. تطبيق Tauri وأداة CLI عميلان لها. الفائدة: اختبار سهل، واستبدال الواجهة متى شئنا، وأداة سطر أوامر شبه مجانية.

### 4.2 هيكل المستودع

```
modmanager/
├─ Cargo.toml              # workspace: core و cli و src-tauri
├─ core/                   # مكتبة Rust بلا Tauri
│  └─ src/
│     ├─ lib.rs
│     ├─ providers/        # modrinth و curseforge خلف trait موحد
│     ├─ downloader/       # طابور و retry و .part و هاش
│     ├─ resolver/         # خطة التثبيت والتبعيات
│     ├─ instances/        # النسخ المعزولة وملف القفل
│     ├─ modpack/          # .mrpack و CurseForge
│     ├─ jar_reader/       # fabric.mod.json و mods.toml
│     ├─ db/               # rusqlite و migrations
│     └─ safety/           # تحقق المسارات والكتابة الذرية
├─ cli/                    # clap فوق core
├─ src-tauri/              # أوامر IPC فقط
│  ├─ src/                 # main.rs و lib.rs و commands.rs
│  ├─ capabilities/
│  └─ tauri.conf.json
├─ src/                    # React: app و features و components و lib
├─ docs/adr/               # سجل القرارات المعمارية
└─ .github/workflows/
```

نبدأ بحزمة `core` واحدة بوحدات داخلية، ونقسمها إلى حزم أصغر فقط حين تكبر وحدة أو يبطؤ البناء.

### 4.3 مخطط المعمارية

الواجهة وأداة الأوامر تستدعيان النواة وحدها، والنواة هي التي تتصل بالمصدرين والملفات وSQLite.

### 4.4 المزوّدون (Providers)

واجهة موحدة (trait) لكل مصدر: `search` و`get_project` و`get_versions` و`get_versions_by_hashes`. يحوّل كل مزوّد ردوده إلى نماذج النواة، فلا تتسرب تفاصيل Modrinth أو CurseForge إلى باقي الكود. إضافة مصدر جديد = كتابة مزوّد واحد.

- **Modrinth (API v2):** ترويسة `User-Agent` تعرّف التطبيق وتتضمن وسيلة تواصل، والتزام بحدود المعدل. نقطتا `version_files` و`version_files/update` تفحصان التحديثات دفعة واحدة بدل طلب لكل مود.
- **CurseForge (API v1):** مفتاح API مطلوب. بعض الملفات تعيد `downloadUrl` فارغاً لأن المؤلف منع التحميل الخارجي، فنفتح للمستخدم صفحة الملف في المتصفح. المودات اليدوية تُعرَّف عبر `fingerprints`.
- **وكيل صغير لاحقاً:** يحمي مفتاح CurseForge من الاستخراج من التطبيق الموزَّع، وهو الاستخدام الوحيد المتوقع لخادم.
- محدّد معدل داخلي، وتخزين مؤقت بمدة صلاحية لنتائج البحث.

### 4.5 محرك التحميل

- طابور بحد أقصى للتزامن (`Semaphore`). التوازي **بين الملفات** هو المهم لأن المودات صغيرة، فلا حاجة لتقسيم الملف الواحد إلى أجزاء.
- إعادة محاولة بتأخير تصاعدي مع عشوائية، وإلغاء نظيف.
- التنزيل إلى ملف `.part` مؤقت، ثم التحقق من الهاش (SHA-1 أو SHA-512 حسب المصدر)، ثم إعادة تسمية ذرّية إلى الوجهة.
- بثّ مباشر إلى القرص دون تحميل الملف في الذاكرة، واستئناف عبر `Range` حيث يدعمه الخادم (اختياري في البداية).
- التقدم يُرسل إلى الواجهة عبر Channel.

### 4.6 محلل التبعيات: خطّط ثم نفّذ

يبني خطة (إضافات وتحديثات وحذف) تُعرض للمستخدم قبل أي تعديل.

1. تصفية الإصدارات حسب إصدار ماينكرافت والـ loader (Fabric / Forge / NeoForge / Quilt).
2. اختيار الإصدار الأحدث وفق قناة مفضلة (release أولاً).
3. المرور على التبعيات: المطلوبة تُضاف تكرارياً، والمتعارضة تُنبّه، والاختيارية تُقترح، والمضمَّنة تُتجاهل.
4. اكتشاف الدورات وتعارض الإصدارات.

تعطيل مود = إعادة تسمية الملف إلى `.jar.disabled`، وهو العرف الشائع في المشغّلات.

### 4.7 المود باكات

- **Modrinth:** ملف `.mrpack` يحوي `modrinth.index.json` (الملفات وروابطها وهاشاتها) ومجلد `overrides`.
- **CurseForge:** ملف `.zip` يحوي `manifest.json` (قائمة `projectID` و`fileID`) ومجلد `overrides`.
- استيراد وتصدير الصيغتين، وحزمة **packwiz** مرحلة لاحقة.
- فك `overrides` يمر بقواعد الأمان في القسم 6.

### 4.8 مودات مثبتة يدوياً

قراءة بيانات الـ jar (`fabric.mod.json` و`META-INF/mods.toml` و`neoforge.mods.toml`)، ثم التعرّف عليها بالهاش لدى المزوّدين لتمكين فحص التحديثات.

## 5. البيانات والتخزين

- جداول SQLite الأساسية: `instances` (الاسم، إصدار ماينكرافت، الـ loader، المسار)، و`installed_mods` (النسخة، المزوّد، معرّفا المشروع والإصدار، اسم الملف، الهاش، مفعّل أم لا، مُدار أم يدوي)، و`api_cache` (المفتاح، الاستجابة، وقت الجلب)، و`downloads` (حالة الطابور وسجلّه).
- الإعدادات في ملف JSON منفصل.
- ملف **قفل لكل نسخة** (`instance.lock.json`) يسجّل الإصدارات والهاشات بدقة، فيمكن إعادة بناء النسخة نفسها لاحقاً أو مشاركتها.
- بيانات التطبيق في المجلد القياسي لكل نظام عبر `directories`؛ لا تُكتب المسارات يدوياً.
- نفعّل وضع WAL في SQLite، ونُدير تغييرات المخطط بترحيلات (migrations) مرقّمة من اليوم الأول.

## 6. الأمان

تُنفَّذ هذه البنود في المرحلة M1 مع أول ملف يُثبَّت، لا بعد بناء الواجهة.

- **فك الحزم:** نستخدم `enclosed_name()` في مكتبة `zip`، ونرفض أي مسار مطلق أو يحوي `..` وأي رابط رمزي، ونضع حدوداً لحجم الفك الكلي وحجم الملف الواحد وعدد الملفات. المود باكات تأتي من مصادر غير موثوقة، فلا نتساهل هنا.
- كل ملف منزَّل يُتحقق من هاشه قبل اعتماده، ويُكتب إلى ملف مؤقت ثم يُعاد تسميته ذرّياً.
- HTTPS فقط، وقائمة بيضاء لنطاقات التحميل المعروفة لـ Modrinth وCurseForge.
- الـ WebView بلا وصول مباشر للملفات ولا للشبكة ولا لـ SQL؛ نفعّل أقل الأذونات (capabilities) ونكتب سياسة CSP صارمة.
- فحص التبعيات بـ `cargo audit` أو `cargo deny` في الـ CI.
- مفتاح CurseForge لا يدخل المستودع أبداً.

## 7. التغليف والتحديث

- **ويندوز:** مثبّت NSIS أو MSI، ويحتاج WebView2 (متوفر عادة، ويمكن تضمين مثبّته). توقيع الكود يقلل تحذيرات SmartScreen.
- **لينكس:** AppImage وdeb وrpm، ويعتمد على WebKitGTK؛ وFlatpak لاحقاً.
- **التحديث التلقائي:** `tauri-plugin-updater`، ويتطلب مفاتيح توقيع خاصة بالتحديثات تُحفظ بأمان.
- **CI:** GitHub Actions بمصفوفة ويندوز وأوبونتو (`tauri-action`) تبني المثبّتات عند كل إصدار.

## 8. بيئة التطوير والإعداد الأولي

**الأدوات**

- Rust عبر `rustup` (قناة stable)، وNode LTS مع pnpm.
- ويندوز: Visual Studio Build Tools (MSVC) وWebView2. لينكس: حزم تطوير WebKitGTK حسب التوزيعة.
- VS Code مع rust-analyzer وTailwind IntelliSense.
- `rustfmt` و`clippy` وBiome؛ واختبارات `cargo test` مع `wiremock` للنواة، وVitest للواجهة.
- Conventional Commits، وكل قرار كبير يُكتب في `docs/adr/`.

**الإعداد الأولي بالترتيب**

1. أنشئ المشروع بالقالب الرسمي: `pnpm create tauri-app` (اختر TypeScript ثم pnpm ثم React ثم TypeScript). لا نبدأ بقوالب طرف ثالث، لنفهم كل سطر.
2. أضف Tailwind 4: `pnpm add tailwindcss @tailwindcss/vite`، ثم `@import "tailwindcss";` في ملف CSS الرئيسي.
3. أضف `@types/node`، وعدّل `vite.config.ts` كما بالأسفل، ثم شغّل `pnpm dlx shadcn@latest init`.
4. أنشئ `Cargo.toml` جذرياً للـ workspace وأضف `core` و`cli`.
5. اكتب أمر IPC تجريبياً بأنواع مولَّدة، ثم ثبّت الـ CI.

`vite.config.ts` (Tailwind 4 مع alias الخاص بـ shadcn):

```ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import tailwindcss from '@tailwindcss/vite';
import path from 'node:path';

export default defineConfig({
  plugins: [react(), tailwindcss()],
  resolve: { alias: { '@': path.resolve(__dirname, './src') } },
  clearScreen: false,
  server: {
    port: 1420,
    strictPort: true,
    watch: { ignored: ['**/src-tauri/**'] },
  },
});
```

`Cargo.toml` الجذري:

```toml
[workspace]
resolver = "2"
members = ["core", "cli", "src-tauri"]
```

`src-tauri/tauri.conf.json` (الحد الأدنى):

```json
{
  "productName": "ModManager",
  "version": "0.1.0",
  "identifier": "com.example.modmanager",
  "build": {
    "beforeDevCommand": "pnpm dev",
    "devUrl": "http://localhost:1420",
    "beforeBuildCommand": "pnpm build",
    "frontendDist": "../dist"
  },
  "app": {
    "windows": [{ "title": "ModManager", "width": 1200, "height": 800 }]
  }
}
```

**قبل إضافة أي مكتبة**، خاصة الحديثة: افتح صفحتها على crates.io وتحقق من تاريخ آخر إصدار وعدد التنزيلات والرخصة وحالة الصيانة. ما يمكن كتابته في أقل من مئة سطر نكتبه بأنفسنا.

## 9. الشاشات

1. **النسخ (Instances):** قائمة وإنشاء.
2. **تفاصيل النسخة:** المودات (تفعيل وتعطيل وتحديث وحذف) والإعدادات.
3. **التصفح:** بحث موحَّد في المصدرين مع مرشحات (الإصدار، الـ loader، الفئة).
4. **المود باكات:** استيراد وتصدير.
5. **التحميلات:** الطابور والتقدم.
6. **الإعدادات:** المسارات، اللغة، الثيم، مفاتيح API.

مبادئ التصميم: ثيم داكن وفاتح، لوحة أوامر واختصارات لوحة المفاتيح، وحالات تحميل وأخطاء واضحة.

1. **M0 الأساس:** المستودع وCargo workspace، وCI يبني على ويندوز وأوبونتو، وأمر IPC تجريبي بأنواع مولَّدة. **المخرج:** التطبيق يفتح على النظامين من ملفات يبنيها الـ CI.
2. **M1 النواة والأمان:** مزوّد Modrinth، ومحرك تحميل بتحقق هاش وكتابة ذرّية، وفك آمن للحزم، وSQLite، وCLI (بحث، تثبيت مع تبعيات، تحديث، حذف). **المخرج:** تثبيت مجموعة مودات حقيقية من سطر الأوامر على النظامين مع التحقق من كل هاش.
3. **M2 الواجهة:** شاشات النسخ والتصفح والتحميلات مع تقدم عبر Channels. **المخرج:** كل التدفقات الأساسية في تطبيق بايثون القديم تعمل في الجديد.
4. **M3 التوسع:** مزوّد CurseForge (مع حالة `downloadUrl` الفارغ وقرار الوكيل)، والمود باكات، والمودات اليدوية. **المخرج:** استيراد `.mrpack` وحزمة CurseForge حقيقيتين وتثبيتهما كاملتين.
5. **M4 الإصدار:** التحديث التلقائي، توقيع الكود، التوزيع، والترجمة. **المخرج:** مثبّتات تعمل وتتحدث تلقائياً على النظامين.

**لاحقاً:** packwiz، والتكامل مع Prism والمشغّل الرسمي، ومشاركة ملفات القفل.

## 13. قواعد هندسية ملزِمة

1. النواة لا تعتمد على Tauri أو أي واجهة.
2. لا `unwrap()` في الكود الإنتاجي؛ الأخطاء أنواع صريحة تُرسل للواجهة برمز يُترجَم.
3. كل ملف منزَّل يُتحقق منه ويُكتب ذرّياً، وكل فك حزمة يمر بتحقق المسارات.
4. كل عملية تعديل تمر بخطة تُعرض أولاً (dry-run).
5. الواجهة لا تصل للملفات أو الشبكة أو SQL إلا عبر أوامر النواة.
6. التقدم عبر Channels وبوتيرة محدودة.
7. لا تُضاف مكتبة قبل فحص صفحتها على crates.io.
8. كل قرار تقني كبير يُسجَّل في ADR.

## 14. ما هو قائم: المواصفات والترحيل

تطبيق بايثون الحالي عامل ومُختبَر، فلا نبدأ كأنه غير موجود.

- **قرار المسار (محسوم):** مشروع جديد بالكامل بـ Rust وTauri وReact. التطبيق القديم **مصدر معرفة فقط** (ميزات وسلوك وحالات حدّية)؛ لا يُبنى عليه ولا يُنقل كوده سطراً بسطر، وتُعاد كتابة كل ميزة مقبولة من وصف سلوكها.
- **SPEC.md (بوابة قبل M1):** ينتجه وكيل ذكاء اصطناعي بقراءة التطبيق القديم للقراءة فقط، ثم تراجعه أنت وتحسم لكل ميزة: نُبقيها أو نحذفها أو نؤجلها. يغطي: المزوّدين وحدود المعدل وإعادة المحاولة، ومعالجة المود باكات وحالاتها الحدّية، وقواعد فك الأرشيف، والتحقق من الهاش، والتبعيات والتعارضات، وكشف الـ loader، وسياسة الترحيل والنسخ الاحتياطي، وبوابة إصدار المخطط (رفض فتح قاعدة بيانات أحدث من المدعوم بدل إتلافها)، وتنقية السجلات من الأسرار.
- **اختبارات مرجعية:** تُنقل حالات اختبار بايثون وبياناتها (ردود API مسجّلة، وملفات `.mrpack` وحزم CurseForge حقيقية) إلى اختبارات Rust. هي المواصفة القابلة للتنفيذ، وتوفّر إعادة اكتشاف الحالات الحدّية.
- **لا يُنقل:** كود الواجهة القديمة وبنيتها الداخلية؛ الواجهة الجديدة تُصمَّم من القسم 9.
- **ترحيل بيانات المستخدم (قرار مفتوح):** كيف تنتقل قاعدة البيانات والبروفايلات؟ الاقتراح: استيراد من الملف القديم عند أول تشغيل مع نسخة احتياطية قبل أي تعديل.
- **مصير التطبيق القديم:** يبقى للقراءة فقط مرجعاً حتى تتحقق مطابقة السلوك، ثم يُؤرشَف.

## 15. أسباب إعادة الكتابة ومعايير نجاحها

سببا إعادة الكتابة هما **الأداء** و**الشكل**، فنقيس نجاح النسخة الجديدة بهما.

**الأداء**

- ضمن بوابة ما قبل M1 نقيس التطبيق القديم: زمن الإقلاع، والذاكرة عند الخمول، وزمن عرض قائمة مودات طويلة، وزمن البحث، وسرعة تثبيت مود باك، وسلاسة الواجهة أثناء التحميل.
- نحدد لكل رقم هدفاً أفضل منه، ونعرف أين العنق الفعلي (الواجهة أم المنطق) قبل أن نقرر ما يستحق إعادة الكتابة.
- **قاعدة القرار بعد القياس:** إن كان البطء في الواجهة والتزامن فالأولوية لطبقة عرض جديدة؛ وإن كان في الإقلاع والذاكرة وفك الأرشيف فنواة Rust مبرَّرة؛ وإن كان محدوداً بالشبكة أو القرص فلا لغة تحله، ونراجع التزامن وإعادة المحاولة.
- **كيف نسجّل القياس:** جهاز واحد ثابت نسجّل مواصفاته (المعالج والذاكرة والقرص وإصدار النظام وإصدارات Python وPySide6).
- ثلاث تشغيلات لكل رقم، ونعتمد الوسيط لا أفضل قيمة.
- نسجّل حجم بيانات الاختبار: عدد المودات في قاعدة البيانات، وعدد البروفايلات، وحجم المود باك المستخدم. ونقيس أكثر من مود باك واحد لأن أحجامها تتفاوت كثيراً.
- نحفظ الأرقام في ملف `docs/baseline.md` داخل المستودع لنقارنها بعد شهور على الجهاز نفسه.
- لا نعلن نجاح M2 قبل مقارنة الأرقام الجديدة بالقديمة على الجهاز نفسه.

**الشكل**

- يُحسم اتجاه بصري قبل M2: مراجع من تطبيقات يعجبنا شكلها، وثيم داكن وفاتح، وقيم تصميم موحّدة (ألوان وخطوط ومسافات).
- تُصمَّم الشاشات الست (القسم 9) قبل برمجتها، ويُراجَع شكلها على النظامين.

**تفاصيل القياس المتفق عليها**

- **عرض قائمة المودات رقمان لا رقم واحد:** زمن مسح القرص وزمن ملء الجدول. الدمج بينهما يخفي مكان الاختناق، وهو ما يحسم هل تكفينا واجهة جديدة أم نحتاج نواة جديدة.
- **الذاكرة بمقياسين** (WorkingSet وPrivateBytes) ومجموعين على كل عمليات التطبيق، لأن WebView2 يتوزع على عدة عمليات.
- **سلاسة الواجهة أثناء التحميل:** نعدّ التجمدات التي تتجاوز 200 مللي ثانية ونسجّل أطولها بدل الانطباع الشخصي. ويُقاس التطبيق الجديد بما يكافئها (فجوات الإطارات أو Long Tasks في الواجهة).
- **خط الأساس السلوكي** في `docs/baseline.md`: عدد الاختبارات الناجحة والفاشلة والمتخطاة وأسماء الفاشلة. نشغّل الاختبارات على نظام ملفات يدعم الروابط الصلبة (NTFS على ويندوز)، فقد تفشل أو تُتخطى بعضها على exFAT بلا علة في التطبيق. ونضيّق أي تأكيد واسع (يقبل أي OSError) عند نقله إلى Rust.

**ما أثبته القياس الأول (مسح ملفات jar)**

- المسح البارد (أول فتح للملفات) أبطأ كثيراً من الدافئ، فنسجّلهما منفصلين لأن الوسيط من ثلاث تشغيلات يمحو هذا الفرق. الأرقام في `docs/baseline.md`.
- الكلفة في فتح الملفات أول مرة (القرص ومضاد الفيروسات) لا في فك الأرشيف، فلا تحلها لغة. هذا الجزء يقع في الفرع الثالث من قاعدة القرار، ولا يبرّر Rust وحده.
- **نتيجة التصميم:** فهرس فحص محلي يخزّن نتيجة قراءة كل jar بمفتاح (المسار، الحجم، وقت التعديل) فلا نعيد فتحه ما لم يتغير، وتسخين في خيط خلفي بدل حجب الواجهة. ولا نعتمد على استثناء مضاد الفيروسات حلاً، لأنه يحتاج صلاحيات ولا نتحكم فيه عند المستخدمين.
- الإقلاع والذاكرة وسلاسة الواجهة أثناء التثبيت لم تُقس بعد، وهي التي تحسم هل نحتاج نواة Rust.
- أي رقم شاذ (مثل أول تشغيل بعد أول فتح للملفات) يُسجَّل ملاحظة منفصلة لا رقماً في الجدول.

**نتائج أولية: الإقلاع والذاكرة والمسح**

- **الإقلاع:** أول تشغيل بارد أبطأ كثيراً من الدافئ، فنسجّلهما منفصلين. الوسيط وحده يخفي تجربة المستخدم بعد تشغيل الجهاز. الأرقام في `docs/baseline.md`.
- **الذاكرة:** لا نَعِد بذاكرة أقل؛ هدفنا ألا تزيد عن التطبيق الحالي، لأن WebView2 يتوزع على عدة عمليات.
- **المسح:** يحلّه الفهرس المخزَّن (القسم أعلاه) لا اللغة.
- **الحكم المرحلي (محدَّث):** حسم المشروع الانطلاق من الصفر بـ Rust وTauri (القسم 14)، فلا نشترط أن يبرّر الأداء وحده هذا القرار. تبقى الأرقام أعلاه ميزانيات نقارن بها النسخة الجديدة، وخاصة الإقلاع البارد.
- **تقدير الإقلاع المتوقع من Tauri غير مثبت:** نقيسه على M0 فوق الجهاز نفسه، وتكلفة التجربة يوم واحد.
